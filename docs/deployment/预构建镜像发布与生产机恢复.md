# GitHub Release 部署与生产机恢复

## 1. 发布制品

生产服务器不克隆 Backend/Admin、不访问容器镜像仓库，也不运行 `docker build`。Backend 仓库的 GitHub Actions `Publish GitHub Release` 对指定的 Backend/Admin Commit 运行完整质量门禁，然后创建包含四个独立资产的 GitHub Release：

```text
wemini-backend-<Backend Commit>.tar.zst
wemini-admin-<Admin Commit>.tar.zst
wemini-deploy-<Release Tag>.tar.gz
SHA256SUMS
```

两个镜像分别保存，单个资产达到 GitHub Release 的 2 GiB 上限时发布立即失败，不会生成一个不可下载的 Release。部署包只包含 Compose、安装脚本、Commit/镜像清单和说明，不包含源码或 Secret。

镜像标签使用完整 Commit，镜像内同时写入相同的 `org.opencontainers.image.revision`。服务器依次验证 Release 总校验和、镜像包内置校验和、镜像标签和 revision。

## 2. 创建 Release

在 Backend 仓库 GitHub Actions 页面手工运行 `Publish GitHub Release`，填写：

- `release_tag`：新的不可变标签，例如 `2026.08.14.1`；已存在的标签拒绝覆盖。
- `backend_ref`：Backend 分支、标签或完整 Commit。
- `admin_ref`：Admin 分支、标签或完整 Commit。

需要恢复一笔已经开始的安装时，从服务器的 `control/source-pins.env` 读取两个 Commit，并原样填入 `backend_ref`、`admin_ref`。工作流以 Draft 创建 Release，全部资产上传成功后才发布。

## 3. 服务器下载和安装

服务器安装 Docker Compose v2、`zstd` 和 GitHub CLI。公开仓库也可从网页下载全部资产；私有仓库使用只读 GitHub Token 登录 `gh`。

```bash
mkdir -p /tmp/wemini-release
cd /tmp/wemini-release

gh release download 2026.08.14.1 \
  --repo BishengTeam/Backend

sha256sum -c SHA256SUMS
tar -xzf wemini-deploy-2026.08.14.1.tar.gz
cd wemini-deploy-2026.08.14.1
./install_release.sh
```

如果普通用户没有 Docker Socket 权限，不要执行 `sudo ./install_release.sh`，只让 Docker 子命令使用 sudo：

```bash
DOCKER_USE_SUDO=1 ./install_release.sh
```

脚本先执行一次 `sudo -v`，Git、校验、配置和 Secret 文件仍归当前部署用户所有。

`install_release.sh` 会：

1. 再次核对两个镜像包的 SHA-256。
2. 通过 `zstd -dc | docker load` 导入镜像。
3. 核对完整 Commit 标签和 OCI revision。
4. 以 `DEPLOY_SOURCE_MODE=release` 启动无源码 Bootstrap Compose。
5. 复用原有网页配置、迁移、种子、恢复包、运行时启动和 UAT 状态机。

部署用户可以直接拥有 Docker 权限，也可以使用 `DOCKER_USE_SUDO=1`；禁止用 `sudo` 运行整个安装器。部署根目录仍需由管理员创建一次：

```bash
sudo install -d -m 0700 \
  -o "$(id -un)" \
  -g "$(id -gn)" \
  /srv/wemini-bootstrap
```

## 4. 人社模板

`报名信息.xlsx`、`工作经历.xlsx` 缺失不阻断 Backend/Admin 部署。脚本会创建并输出默认目录：

```text
/srv/wemini-bootstrap/assets/renshe
```

缺失期间仅人社批次导出不可用。补齐两个正式模板并确保容器用户可读后即可恢复，不需要重新迁移或安装。

## 5. 现场构建中断后的无损恢复

旧脚本卡在 `docker build` 时：

1. 在原终端按一次 `Ctrl+C`。
2. 不删除 `control/`、`installation/`、数据库、Docker Volume 或恢复包。
3. 读取固定 Commit；该文件不含 Secret：

```bash
sudo sed -n \
  -e '/^BACKEND_COMMIT=/p' \
  -e '/^ADMIN_COMMIT=/p' \
  /srv/wemini-bootstrap/control/source-pins.env
```

4. 使用两个 Commit 手工创建 GitHub Release。
5. 下载四个资产并执行 `SHA256SUMS` 校验。
6. 如果旧脚本曾使用 root 运行，只修改已存在的源码/控制目录属主，不要修改数据库 Volume：

```bash
sudo chown -R "$(id -un):$(id -gn)" \
  /srv/wemini-bootstrap/Backend \
  /srv/wemini-bootstrap/Admin \
  /srv/wemini-bootstrap/control \
  /srv/wemini-bootstrap/installation
```

7. 执行 Release 中的 `install_release.sh`。其 Commit 必须与已有 `source-pins.env` 完全一致，否则会拒绝覆盖。状态机会从保存阶段继续。

## 6. 安全边界

- Release 标签不可复用或覆盖。
- Release 不包含微信、支付、OSS、数据库密码或任何运行 Secret。
- 镜像资产不进入 Git 历史。
- 服务器不执行源码测试、npm 安装或镜像构建。
- 安装器不删除数据库、Redis、Secret 或 Docker Volume。
- `build` 模式仅保留给开发环境，不再属于生产发布流程。
