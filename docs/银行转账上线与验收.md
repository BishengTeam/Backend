# 银行转账订单上线与验收

本次覆盖 Backend、Admin、Platform。三个仓库需要一起发布；本文件不代表已经部署或配置真实收款账户。

## 行为

- H3C、NISP、人社及通用认证的新现金订单使用 `bank_transfer`，保存创建时的收款账户和联系人快照。批次联系人优先；默认联系人兜底。
- 课程、题库现金购买保持关闭，原积分兑换服务不变。合法零元报名直接承接原流程；优惠券折为零元的订单使用专门的零元确认入口，不提交转账凭证。
- 凭证支持 JPG、PNG、PDF，单文件不超过 10 MB，每次提交 1–3 份。保存在现有私有存储的 `ALIYUN_OSS_PREFIX/offline-payments/` 下，只能通过带登录鉴权的接口读取。
- 上传不代表付款。核账要求实际金额、银行时间、流水、当前凭证版本及备注；金额不符转异常，不发放权益。每次提交与补交保留独立版本。
- 默认首次提交 24 小时、补交 48 小时，均可在收款设置中配置；首次截止不超过批次截止。补交期限由后台返回，不延长普通报名入口。
- 提交凭证后停止普通超时关闭、冻结优惠券金额，禁止普通取消。补交逾期转异常，继续保留名额，待明确关闭或实际退款完成后释放。
- 确认到账仅推进原报名资料审核；未替代初审、补正、导出和终审／外审。
- 专用退款审批对银行订单只生成／保留待线下退款记录。管理员实际退款后，上传凭证并登记流水，才将退款及报名转为完成状态。
- 已关闭、批次取消等资金异常不恢复订单或名额。后台可登记真实到账及原路退回的流水、时间、金额和退款凭证，完成异常处理。

## 发布顺序

1. 执行数据库迁移到 `pay002_offline`。它新增独立财务记录，保留既有订单和材料，不删除历史数据。
2. 发布支持渠道分流的 Backend 和 Admin。生产环境须启用现有 `RENSHE_STORAGE_TYPE=aliyun_oss` 私有存储，并允许配置前缀下的凭证读写；未启用时新现金订单会被阻止。微信查单、回调及退款配置必须继续保留，用于历史交易。
3. 发布并验证小程序的新付款页和订单入口。新订单预支付入口已停止，不再调用微信支付；切换期间应暂停新现金报名，避免旧版小程序展示旧按钮。
4. 超级管理员在「订单管理→收款设置」重新认证后填写真实账户和电话／微信，并核对各批次联系人。未配置时新现金订单会被阻止，系统不会使用示例收款账户。
5. 完成真机验收后开放新报名。既有待核账订单、补交和退款始终可继续处理。

环境变量 `BANK_TRANSFER_NEW_ORDERS_ENABLED=false` 只暂停新现金订单，不关闭已有银行订单的核账、异常和退款接口。两套 Compose 都透传此开关。

历史正价订单只有存在微信交易号时才迁移为 `wechat`；已结算的零价订单迁移为 `free`，其他保留 `unknown`，不可据此直接向银行转账。使用 `scripts/audit_order_channels.py` 列出待核实的订单 ID、类型、金额及状态，不输出姓名和证件材料。没有提供自动将存量微信待支付订单转为银行订单的入口；需先确认旧渠道结果并关单，避免重复收款。

## 权限与操作

独立权限为 `offline:view`、`offline:confirm`、`offline:return`、`offline:refund`、`offline:settings`。默认只有超级管理员的 `*` 权限可以执行资金操作，原 `order:list` 不获得凭证或收款确认权限。到账确认、实际退款和异常款退回需要管理员重新认证；修改收款账户只允许重新认证的超级管理员。

订单详情抽屉复用现有页面；三个认证的退款工作台新增支付方式及「登记线下退款」，普通订单的退款审批也在原订单详情中完成。报名材料与资金凭证分别鉴权。

每日收退款统计按 `APP_TIMEZONE` 自然日汇总资金发生记录：银行转账使用 `OfflineBankEntry.bank_time`，微信收款使用 `Order.paid_at`，微信退款使用三个认证退款表及迟到款退款任务的 `succeeded_at`。涉及订单数按当日收退款去重，同一订单收款和退款可发生在不同日期。订单创建时间及当前状态不决定历史流水归属。缺少实际时间、没有成功退款记录的历史款项（包括旧通用订单退款）不计入，不能用订单状态补算；该统计不能当作完整历史银行账单。

核账及退款以订单锁串行化；同一收款账号的同一银行流水只能被一个订单认领。凭证版本、幂等请求标识及唯一约束均在数据库事务内校验，业务状态随同事务提交。异常金额不支持部分核销、多笔合并或一笔覆盖多单。

## 批次内报名办理

H3C、NISP、人社批次工作台默认展示全部报名，独立提供核账状态和报名审核状态筛选。点击「办理」进入统一侧边窗，先核账，再审核；订单管理仍可集中核账。凭证预览和下载沿用独立财务权限，认证审核权限不会自动获得财务权限。

侧边窗只使用服务端 `payment_summary.review_payment_allowed` 解锁审核。确认到账后，重新读取付款、报名详情及列表；刷新失败时锁定审核并提供重试。切换报名会重建办理组件，避免上一条材料和操作串入。认证办理中不增加通用退款捷径，仍使用各认证现有退款入口。

初审、打回补正、终审／外审、审核结果更正及批量审核调用链均在事务内检查付款前提。银行订单须有匹配当前凭证版本、金额和账户的到账记录；历史微信及零元订单须有有效的系统付款记录。资金异常、退款申请、冻结、已关闭或关联不一致会阻止审核，不能通过直接请求或批量操作绕过。此变更无需新增数据表或状态枚举，需同时更新后端和 Admin；小程序不新增页面。

## 验证

`tests/integration/db/test_offline_payment_flow.py` 必须设置独立的 `TEST_DATABASE_URL`（asyncpg）和 `TEST_DATABASE_URL_SYNC`，在已迁移的真实 PostgreSQL 中执行。测试覆盖并发确认、跨订单重复流水、补交与旧版核账并发、提交与超时并发、批次取消与确认并发、三个认证的收款／退款分派、异常款退回、私有附件归属及账户快照。

上线前仍需真实银行回单核对，以及安卓、鸿蒙、iOS 微信真机验证上传、预览、联系方式、窄屏与底部安全区。开发者工具和组件预览不能替代这些验收。

已产生线下订单后，不能回退到不认识 `bank_transfer` 的服务版本，也不能删除财务表或覆盖已生成材料。迁移明确阻止破坏性降级；可用上述开关暂停新现金订单，保留核账和退款能力。
