## 二审新发现

### 发现 1（🔴 中）：Training — `AdminTrainingListItem` 缺 `description`

**与批次 2 一审 Activity 问题完全同构。**

| | Activity（批次2一审） | Training（本次二审） |
|---|---|---|
| 模型有 `description` | ✅ | ✅ |
| 列表 Schema 有 `description` | ❌（一审前） | ❌ |
| 用户端可见 | `/api/activities` | `/api/training` |
| 聚合端可见 | `/api/zones` → activities | `/api/zones` → trainings |
| 修复方式 | 添加 `description: str \| None = None` | 待修 |

**影响范围**：

| 接口 | 使用 Schema | 是否受影响 |
|------|-----------|-----------|
| `GET /api/training`（用户端培训列表） | `AdminTrainingListItem` | ❌ 用户看不到描述 |
| `/api/zones` → `zones["training"].trainings`（首页聚合） | `AdminTrainingListItem` | ❌ 首页看不到描述 |
| `GET /admin/trainings`（管理端列表） | `AdminTrainingListItem` | ❌ 管理员也看不到描述 |

三个接口全部受影响，因为 **Training 没有独立的用户端 Schema，`AdminTrainingListItem` 被三端共用**。

**证据**：
- 模型：`app/domain/content/src/model/training.py:13` — `description: Mapped[str | None] = mapped_column(Text)`
- Schema：`app/schemas/admin_training.py:33` — `AdminTrainingListItem` 无 `description` 字段

### 发现 2（🟡 低）：Training — 命名不对称，唯一复用管理端 Schema 的实体

9 个核心实体的用户端/管理端 Schema 对照：

| 实体 | 用户端 Schema | 管理端 Schema | 关系 |
|------|-------------|-------------|------|
| User | `UserProfile` | `AdminUserListItem` | 独立 |
| Order | `OrderResponse` | `OrderResponse`（复用） | 共享 |
| Course | `CourseListResponse` | `AdminCourseListItem` | 独立 |
| Activity | `ActivityResponse` | `AdminActivityListItem(ActivityResponse)` | 继承 |
| Certification | `CertificationDetailResponse` | `AdminCertificationListItem(CertificationDetailResponse)` | 继承 |
| Quiz | `QuizQuestionResponse` | `AdminQuizQuestionResponse` | 独立 |
| Zone | `ZoneBrief` | `AdminZoneListItem` | 独立 |
| Job | `JobResponse` | `AdminJobListItem` | 独立 |
| **Training** | **无** | `AdminTrainingListItem` | **管理端 Schema 被用户端复用** |

Training 是唯一一个「用户端接口使用名为 `Admin*` 的 Schema」的实体。这不影响功能，但：
- 命名传达了错误的语义（管理端 Schema 不应直接暴露给用户端）
- 如果未来需要区分用户端/管理端字段，改动成本高
- 与其余 8 个实体的模式不一致

> **经验 E1**：审计时对「Admin* Schema 被用户端接口引用」的模式做专项扫描。`grep_files` 搜索 `AdminTrainingListItem` 在 `app/api/` 下非 admin 路径中的引用，即可发现此类不对称。

### 发现 3（🟡 低）：审计范围遗漏 — Training 在批次 2 和批次 3 中均未被覆盖

**批次 2** 审计了 9 个核心实体（User, Order, Course, Certification, Quiz, Activity, Zone, Coupon, Job），**但不含 Training**。

**批次 3** 审计了 8 个嵌套/扁平结构（HomeAggregationResponse, CourseEnrollmentResponse, QuizRecordQuestionResponse, OrderDetailResponse, UserProfileDetail, LoginResponse, AdminUserListItem, admin users 子资源），**Training 不在其中**。

Training 之所以被遗漏，是因为它跨越了批次的审计边界：
- 批次 2 审「实体 Schema 统一表达」— Training 只有一个 `AdminTrainingListItem`，看起来「统一」（实际是缺失用户端 Schema）
- 批次 3 审「结构归属」— Training 没有嵌套结构，不触发审计条件

**两个批次各自看了自己关注的反模式，都没发现 Training 的问题。**

> **经验 E2**：批次划分可能造成审计盲区。单一实体如果恰好不触发任何一个反模式（没有表达分裂、没有结构散落、没有路径冗余），它会被所有批次「合法跳过」。建议在每个批次的末尾增加**全覆盖清单核对**：列出系统中所有实体的 API 端点，逐项标记是否被本批次覆盖。

## 可复用的审查经验

### 本次新增

- [ ] **Admin* Schema 用户端引用扫描**：搜索 `grep 'Admin\w+ListItem|Admin\w+Response'` 在 `app/api/` 下非 admin 路径中的引用。`Admin*` Schema 被用户端接口引用 → 标记「命名不对称」
