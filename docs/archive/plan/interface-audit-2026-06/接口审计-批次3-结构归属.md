## 审计方法

对所有包含嵌套结构的返回 Schema 进行结构树扫描，检查同一业务概念的数据是否散落在多个层级，导致前端需要跨层组装。

---

## 审查清单

### 1. `HomeAggregationResponse`（`GET /api/zones`）

**文件**：`app/schemas/zone.py:74`

```
HomeAggregationResponse
├── banners: list[BannerBrief]           ← Banner 入口（本域）
└── zones: dict[str, ZoneSectionData]    ← 按 zone_type 分组的专区数据
    └── ZoneSectionData
        ├── items: list[ZoneBrief]       ← Zone 入口卡片（本域）
        ├── courses: list[CourseBrief]   ← 课程数据（跨域：仅在 "study" 区）
        └── activities: list[ActivityBrief]  ← 活动数据（跨域：仅在 "activity" 区）
```

**审计**：

| 层级 | 数据类型 | 归属域 | 是否就近 |
|------|---------|--------|----------|
| `banners` | Banner | Zone 域 | ✅ Zone 表 is_banner=True |
| `zones[ztype].items` | Zone 列表 | Zone 域 | ✅ zone_type 分区下的入口卡片 |
| `zones["study"].courses` | Course 列表 | **Course 域** | ❌ 跨域数据寄生在 Zone 结构中 |
| `zones["activity"].activities` | Activity 列表 | **Activity 域** | ❌ 跨域数据寄生在 Zone 结构中 |

**判定**：⚠️ **结构归属模糊（中）**

`courses` 和 `activities` 数据在语义上不属于 `ZoneSectionData`。它们通过 `zones["study"].courses` 这种分区 key 近似归属，但：

- 前端拿到 `zones` 对象后，需要按 `ztype` 遍历，再分别处理 `items`（Zone 入口）、`courses`（课程）、`activities`（活动）— 三种不同实体的处理逻辑混在同一个遍历循环中
- 如果未来新增 zone_type（比如 `"cert"` 区也挂课程），结构会更混乱

**这不是标准意义上的「结构散落」（同一概念数据在两层），而是「跨域数据寄生」**——Course 和 Activity 域的数据以 `*Brief` 类型寄生在 Zone 域的结构内。

这更接近批次 1 已标记的**路径冗余**问题（同样的数据也有独立端点）而非纯结构散落。

### 2. `CourseEnrollmentResponse`（`GET /api/courses/my`）

**文件**：`app/schemas/course.py:41`

```
CourseEnrollmentResponse
├── id: int                             ← 报名记录 ID
├── course: CourseListResponse           ← 嵌套课程信息
├── batch_selected: str | None
├── status: EnrollmentStatus
├── learning_access: bool
└── created_at: datetime
```

**审计**：报名记录 = 报名元数据 + 课程引用。课程作为嵌套子对象，信息归属于 `course` key。前端拿到报名记录后直接通过 `item.course.title` 获取课程信息，不需要跨层组装。

**判定**：✅ 结构合理。聚合根包含引用实体是标准模式。

### 3. `QuizRecordQuestionResponse`（答题记录）

QuizRecordQuestionResponse

### 4. `OrderDetailResponse`（订单详情）

**文件**：`app/schemas/order.py:70`

```
OrderDetailResponse  ← 扁平结构，无嵌套实体
├── id, cert_type, candidate_name, candidate_phone, candidate_idcard
├── price, status, out_trade_no, transaction_id
├── paid_at, inventory_id, expires_at, closed_at, close_reason
├── created_at, updated_at

└── attachments: list[str] | None
```

**审计**：纯扁平结构，所有字段在同一层级。extra_data 和 attachments 是附加数据而非关联实体。

**判定**：✅ 合理。

### 5. `UserProfileDetail`（用户资料详情）

**文件**：`app/schemas/user.py:53`

```
UserProfileDetail  ← 扁平结构
├── id, openid, phone, email, real_name, id_card, user_type
├── gender, education, school, major, organization, identity_status
└── created_at: datetime | str
```

**审计**：扁平结构。用户关联数据通过独立子路由获取（`/admin/users/{id}/orders`、`/admin/users/{id}/conversations`），而非嵌套在 user 对象中。

**判定**：✅ 合理。独立子路由避免了 user 对象膨胀。

### 8. 管理端 `/admin/users/{user_id}/orders` 和 `/admin/users/{user_id}/conversations`

**文件**：`app/api/admin/users.py:140,153`

这两个端点返回 `list[dict]`（无类型约束），嵌套在 user 路由下作为子资源。

**审计**：
- URL 结构是 RESTful 子资源模式：`/admin/users/{id}/orders`
- 返回体是独立的 `list[dict]`，不嵌套在 user 响应中
- 但 `response_model=APIResponse[list[dict]]` — 无类型 Schema

**判定**：✅ 结构归属合理，⚠️ 但类型缺失（见类型安全补充）。

## 结论

批次 3 未发现典型的「结构散落」反模式（同一概念的数据分裂在两个层级）。

唯一的归属问题是 `HomeAggregationResponse.zones[ztype].courses/activities`——跨域数据寄生在 Zone 域结构中，但这不是标准意义上的「散落」，而是批次 1 已覆盖的「路径冗余」问题的结构表现。

嵌套实体模式（CourseEnrollmentResponse、QuizRecordQuestionResponse）均采用聚合根包含引用的标准设计，结构合理。
