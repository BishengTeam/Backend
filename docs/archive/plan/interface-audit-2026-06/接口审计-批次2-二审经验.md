## 二审新发现

### 发现 1：「补字段修复」的连锁反应——收敛即重复

**修复路径**：一审标记「管理端缺 X 字段」→ 直接在管理端 Schema 上加字段 → 修复完成。

**连锁反应**：补完后用户端和管理端字段集完全重合，但仍然是两个独立 Pydantic 类型。

**Activity — 已收敛为完全一致的 10 字段**：

| Schema | 文件 | 字段 |
|--------|------|------|
| `ActivityResponse` | `schemas/activity.py:7` | id, title, description, cover_url, location, start_time, end_time, max_participants, **is_active**, **created_at** |
| `AdminActivityListItem` | `schemas/admin_activity.py:28` | id, title, **description**, cover_url, location, start_time, end_time, max_participants, is_active, created_at |

两个 Schema **字段名、类型、默认值完全一致**，且 `model_config = {"from_attributes": True}` 也一致。零差异，但零复用。

**Certification — 字段已对齐但继承关系不对称**：

| Schema | 文件 | 字段 | 继承 |
|--------|------|------|------|
| `CertificationDetailResponse` | `schemas/certification.py:22` | id, name, chinese_name, code, vendor, requires_xuexin, pay_first, created_at, updated_at, is_active | 继承 `CertificationResponse` + 3 字段 |
| `AdminCertificationListItem` | `schemas/admin_certification.py:6` | id, name, chinese_name, code, vendor, requires_xuexin, pay_first, is_active, created_at, updated_at | **独立定义**，无继承 |

10 个字段完全一致，但 `CertificationDetailResponse` 通过继承 `CertificationResponse` 获得基类字段，`AdminCertificationListItem` 是平铺定义。

> **经验 E1（与批次 1 二审 E1 对称）**：batch 1 二审发现「修复表达分裂 → Schema 膨胀（万能容器）」，batch 2 二审发现「修复表达分裂 → Schema 收敛为重复定义」。两条路径不同，根因相同：**修复时只关注了目标 Schema 缺什么，没关注修复后两端的整体关系**。修复前问：「两个 Schema 是否表达了同一实体？」修复后还应问：「两个 Schema 是否可以合并？」

### 发现 2：管理端 `vendor` 从 Literal 退化到 `str`

| Schema | vendor 类型 |
|--------|------------|
| `CertificationResponse` | `Vendor = Literal["H3C", "深信服", "NISP", "人社", "SmokeVendor"]` |
| `CertificationDetailResponse(CertificationResponse)` | 继承 `Vendor` |
| `AdminCertificationListItem` | **`str`** |
| `AdminCertificationCreate` | **`str`** |
| `AdminCertificationUpdate` | **`str`** |

管理端三个 Schema 全部使用 `str`，丢失了 `Literal` 类型约束。这不影响运行时 JSON 输出（都是字符串），但意味着 IDE 自动补全和类型检查器无法在管理端校验 vendor 值的合法性。

**根因**：`CertificationResponse` 在 `schemas/certification.py` 中定义 `vendor: Vendor`，而管理端 Schema 在 `schemas/admin_certification.py` 中独立定义 `vendor: str`，未复用基类。

> **经验 E2**：审计 Schema 时，对 `Literal` / `Enum` 类型字段做跨文件一致性检查。如果某个字段在用户端有严格约束（Literal），管理端应复用同一个类型或至少保持一致。

### 发现 3：修复后的字段对齐状态总览

对所有 9 个实体做二审后的最终状态汇总：

| 实体 | 用户端列表 Schema | 管理端列表 Schema | 关系 | 判定 |
|------|------------------|------------------|------|------|
| User | `UserProfile` (4 字段) | `AdminUserListItem` (5 字段) | 管理端多 is_active | ✅ 合理差异 |
| Order | `OrderResponse` (15 字段) | `OrderResponse` **（复用）** | 完全一致，同一个类型 | ✅ 最佳实践 |
| Course | `CourseListResponse` (7 字段) | `AdminCourseListItem` (12 字段) | 管理端多 video_url, batches, teacher_contact, is_active, created_at | ✅ 合理差异 |
| **Activity** | `ActivityResponse` (10 字段) | `AdminActivityListItem` (10 字段) | **完全一致，两个独立类型** | ⚠️ 重复定义 |
| **Certification** | `CertificationDetailResponse` (10 字段) | `AdminCertificationListItem` (10 字段) | **完全一致，一个继承一个独立** | ⚠️ 重复定义 + vendor 类型退化 |
| Quiz | `QuizQuestionResponse` (6 字段) | `AdminQuizQuestionResponse` (9 字段) | 管理端多 correct_answer, created_at, updated_at | ✅ 安全设计 |
| Zone | `ZoneBrief` (7 字段) | `AdminZoneListItem` (12 字段) | 管理端多管理字段 | ✅ 合理差异 |
| **Job** | `JobResponse` (9 字段) | `AdminJobListItem` (10 字段) | 管理端多 is_active，字段对齐 | ✅ 合理差异 |
| Coupon | `CouponResponse` (9 字段) | `AdminCouponListItem` (9 字段) | **不同实体**（用户券 vs 券模板） | ✅ 实体不同 |

**总结**：9 个实体中，7 个状态良好，2 个（Activity、Certification）存在「收敛后的重复定义」——用户端和管理端 Schema 已经完全一致，但没有合并。

## 可复用的审查经验

### 本次新增的检查项

- [ ] **修复后收敛检查**：当用户端和管理端的列表 Schema 字段集完全一致时，是否仍然是两个独立类型？→ 标记「可合并」
- [ ] **Literal/Enum 跨文件一致性**：用户端有 `Literal[...]` 约束的字段，管理端是否退化为了 `str`？→ 标记「类型退化」
- [ ] **管理端创建/更新 Schema 与列表 Schema 的字段覆盖**：`Admin*Create` / `Admin*Update` 中的字段是否在 `Admin*ListItem` 中都有对应？（防止「能创建但列表看不到」的情况）

### 从批次 1 二审继承的检查项

- [ ] **连锁反应**：修复后检查被修改 Schema 的所有引用点
- [ ] **跨模块配置一致性**：Schema 字段集 ↔ Service 使用的字段集是否一致
- [ ] **伪装 lookup table**：≥3 个同构 if/elif 分支

## 对后续批次的影响

- Activity 和 Certification 的重复定义属于低严重度问题，不阻塞功能，可以在后续 Schema 重构中统一处理
