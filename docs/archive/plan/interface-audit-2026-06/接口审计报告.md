## 4. 交叉验证

### 4.1 遗漏检查

对前三批次未覆盖的模块进行扫尾检查，确认不存在遗漏的反模式：

| 模块 | 扫尾结果 |
|------|---------|
| `/api/points` | 仅积分流水，无跨域依赖 ✅ |
| `/api/chat` | 独立 AI 对话，无实体交叉 ✅ |
| `/api/collection` | 收藏夹，独立模块 ✅ |
| `/api/ticket` | 工单，独立模块 ✅ |
| `/api/competition` | 竞赛，独立模块 ✅ |
| `/api/payment` | 支付，依赖 Order Schema，由 Order 通过 ✅ |
| `/api/share` | 分享，独立模块 ✅ |
| `/api/training` | 培训，结构与 Activity 相似，但当前无跨域引用 ✅ |
| `/api/coupon` | 优惠券，用户券/券模板分离 ✅ |
| `/api/upload` | 上传，纯基础设施 ✅ |

## 5. 修复建议

### P1/P2：路径冗余（`/api/zones` courses/activities）

**问题**：聚合接口返回的课程/活动数据与独立端点数据重叠。

**方案 A（推荐）**：聚合层只做编排
- 从 `ZoneSectionData` 中移除 `courses` 和 `activities` 字段
- 聚合接口仅返回 `items: list[ZoneBrief]`（Zone 入口卡片）
- 前端在获得 zone_type 后，自行调用 `/api/courses` 或 `/api/activities` 获取内容数据
- **变更量**：~20 行（schema + service），前端需配合

**方案 B**：保留聚合但统一 Schema
- 保留 `courses`/`activities` 在聚合接口中
- 将 `CourseBrief` 改为复用 `CourseListResponse`，`ActivityBrief` 改为复用 `ActivityResponse`
- 标记聚合接口为 BFF 层（Backend For Frontend），明确定义它是编排层而非数据源
- **变更量**：~5 行（删除 Brief 类型，改 import），前端无需改动

### E1：Activity 3 变体表达分裂

**方案**：
1. 在 `AdminActivityListItem` 中补充 `description: str | None = None` 字段
2. 让 `AdminActivityListItem` 继承 `ActivityResponse`，或至少字段对齐
3. 删除 `ActivityBrief`（在修复 P1/P2 方案 A 时一并删除，或在方案 B 时改为复用 `ActivityResponse`）

**变更量**：~10 行

### E2：Job 管理端缺 contact_info

**方案**：在 `AdminJobListItem` 中补充 `contact_info: str | None = None` 字段。

**变更量**：~1 行

### D1：CourseBrief 重复定义

**方案**：删除 `CourseBrief`，所有引用处改为 `CourseListResponse`。

**变更量**：~5 行

### E3/T1/T2/A1：低优问题

建议在后续迭代中修复，不阻塞当前修复。
