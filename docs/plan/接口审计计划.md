### 1.2 聚合接口关键 Schema

**`HomeAggregationResponse`（`/api/zones`）：**

```text
HomeAggregationResponse
├── banners: list[BannerBrief]           # Zone 表中 is_banner=True 的条目
└── zones: dict[str, ZoneSectionData]    # 按 zone_type 分区
    └── ZoneSectionData
        ├── items: list[ZoneBrief]       # Zone 入口卡片
        ├── courses: list[CourseBrief]   # 课程数据（仅在 study 区）
        └── activities: list[ActivityBrief]  # 活动数据（仅在 activity 区）
```

**`AdminStatisticsService.dashboard()` 返回结构（`/admin/statistics/dashboard`）：**

```python
{
    "total_users": int,
    "total_orders": int,
    "recent_orders_30d": int,
    "paid_orders": int,
    "revenue_fen": int,
    "recent_revenue_30d_fen": int,
    "conversion_rate": float,
}
```

> 注意：该接口 `response_model=APIResponse`（无泛型约束），返回类型为裸 `dict`。

### 1.3 统一响应格式

所有接口通过 `APIResponse[T]` 包裹：

```json
{ "code": 0, "message": "ok", "data": { ... } }
```

分页接口通过 `PaginatedData[T]`：

```json
{ "code": 0, "message": "ok", "data": { "items": [...], "total": 150, "page": 1, "page_size": 20 } }
```

### 1.4 已知可疑信号

| 信号 | 位置 | 对应反模式 |
|------|------|-----------|
| `/api/zones` 同时承载聚合（Banner + courses + activities）和专区 Zone 列表透传 | `app/api/zone.py` | #1 职责混合 |
| `HomeAggregationResponse` 中 `ZoneSectionData.courses` 与 `/api/courses` 独立端点返回同类数据 | `app/schemas/zone.py` vs `app/api/courses.py` | #4 路径冗余 |
| `HomeAggregationResponse` 中 `ZoneSectionData.activities` 与 `/api/activity` 独立端点返回同类数据 | `app/schemas/zone.py` vs `app/api/activity.py` | #4 路径冗余 |
| `CourseBrief` / `ActivityBrief` 字段数可能小于独立端点返回的完整 Schema | `app/schemas/zone.py` vs `app/schemas/course.py` / `app/schemas/activity.py` | #3 表达分裂 |
| `/admin/statistics/dashboard` 返回裸 dict，未使用类型化 response_model | `app/api/admin/statistics.py` | 类型安全 |

## 2. 审计批次

### 批次 1：聚合层边界审计（反模式 #1 职责混合 + #4 路径冗余）

**目标**：检查聚合/看板接口是否混入单域透传职责，聚合层返回的数据是否与独立端点存在交集。

**审计对象：**

| 编号 | 接口 | 文件 | 审计重点 |
|------|------|------|----------|
| A1 | `GET /api/zones` | `app/api/zone.py` | 返回的 `HomeAggregationResponse` 中各子实体是否与独立端点数据重复 |
| A2 | `GET /admin/statistics/dashboard` | `app/api/admin/statistics.py` | 看板统计是否可从已有独立接口计算得出（属于聚合还是冗余） |

**审计步骤：**

1. 对 A1：
   - 读取 `HomeAggregationResponse` 完整 Schema（`app/schemas/zone.py`）
   - 列出其中所有子实体类型：`BannerBrief`, `ZoneBrief`, `CourseBrief`, `ActivityBrief`
   - 对每个子实体，搜索是否存在独立的 CRUD 端点返回同类数据
   - 对比聚合端点返回的字段与独立端点返回的字段：是否存在字段差异（表达分裂）
   - 标记「路径冗余」：若同一数据可从聚合端点和独立端点两条路径获取
   - 标记「职责混合」：若聚合端点的 URL 前缀（`/zones`）下同时承载聚合和列表透传

2. 对 A2：
   - 读取 `AdminStatisticsService.dashboard()` 返回的完整结构
   - 列出每个统计指标的数据来源（`User`, `Order` 表的聚合函数）
   - 判断是否存在可通过已有独立接口获取的数据（如 total_users 是否等于 `/admin/users` 列表的 total）
   - 判断 dashboard 返回结构是否可作为独立 API 的替代路径

**输出：** 「聚合接口 ↔ 独立端点」交点矩阵 + 问题清单

**预估工时**：小（2 个聚合接口 + ~10 个独立端点交叉比对）

---

### 批次 2：核心实体 Schema 统一表达审计（反模式 #3 表达分裂）

**目标**：检查同一实体在不同接口中是否使用同一 Schema，是否存在「同一实体多种面孔」。

**审计对象**（按接口数量排序）：

| 实体 | 涉及接口 |
|------|----------|
| User / UserIdentity | `/api/user/*`, `/admin/users/*` |
| Order | `/api/orders/*`, `/api/payment/*`, `/admin/orders/*` |
| Course | `/api/courses/*`, `/api/zones`(CourseBrief), `/admin/courses/*` |
| Certification | `/api/cert/*`, `/admin/certifications/*` |
| Quiz | `/api/quiz/*`, `/api/collections/*`, `/admin/quiz/*` |
| Activity | `/api/activity/*`, `/api/zones`(ActivityBrief), `/admin/activities/*` |
| Zone | `/api/zones`(ZoneBrief), `/admin/zones/*` |
| Coupon | `/api/coupons/*`, `/admin/coupons/*` |
| Job | `/api/jobs/*`, `/admin/jobs/*` |

**审计步骤：**

1. 对每个实体，列出所有引用该实体 Schema 的接口和 `response_model`
2. 比较每个接口使用的 Schema 类型是否一致：
   - 字段名是否相同
   - 字段数量是否相同
   - 字段类型是否相同
   - 可选/必选标记是否一致
3. 标记「表达分裂」：同一实体出现 ≥2 个不同 Schema 的接口
4. 特别关注聚合接口中的 `*Brief` 类型（如 `CourseBrief`、`ActivityBrief`）与独立端点完整 Schema 之间的差异

**输出：** 「实体 → Schema 类型 → 使用接口」映射表 + 分裂点标注

**预估工时**：中（9 个实体 × 平均 4 个接口 × 字段逐项对比）

---

### 批次 3：结构归属审计（反模式 #2 结构散落）

**目标**：检查返回结构中同一概念的数据是否散落在多个层级，导致前端需要跨层组装。

**审计对象**（优先级排序）：

| 优先级 | 接口 | 原因 |
|--------|------|------|
| 高 | `GET /api/zones` → `HomeAggregationResponse` | 聚合接口：Zone 入口 + 关联数据分属不同 key |
| 高 | `GET /api/orders/{id}` → `OrderDetailResponse` | 订单详情含嵌套实体 |
| 高 | `GET /api/user/profile` → `UserProfileDetail` | 用户信息含多子实体 |
| 中 | 列表接口返回的 item 结构 | 是否存在「列表摘要字段」和「详情字段」在不同层级 |

**审计步骤：**

1. 对每个目标接口，提取返回 Schema 的 JSON 结构树（key 层级 + 类型）
2. 标记同一业务概念出现在两个不同层级 key 的情况
3. 标记「元数据在父级、内容在子级」的分裂模式
4. 对 Zone 聚合，判断 `zones[ztype].items` + `zones[ztype].courses` + `zones[ztype].activities` 的结构是否合理：
   - zones 按 zone_type 分组 → 合理
   - 每个 zone_type 下 courses/activities 是否应属于各自的独立子路由

**输出：** 结构树 + 散落点标注

**预估工时**：中（约 15 个嵌套返回结构扫描）

---

### 批次 4：全链路拓扑审计 + 汇总报告

**目标**：整合前三批次结果，绘制路由拓扑图，执行交叉验证，输出最终审计报告。

**审计步骤：**

1. 绘制 `/api/*` 和 `/admin/*` 的路由拓扑图（实体 ↔ 端点映射矩阵）
2. 用批次 1-3 的结果标注反模式位置
3. 验证是否存在批次 1-3 遗漏的路径冗余或表达分裂
4. 按反模式分类汇总所有问题
5. 为每个问题评定严重程度：
   - **严重**：前端已报告组装困难 / 数据不一致
   - **高**：明确违反审计标准，且影响范围 ≥3 个接口
   - **中**：违反标准但影响面小
   - **低**：边界模糊，可讨论
6. 输出修复建议：每个问题的推荐修复方向和预估变更量

**输出：** 综合审计报告（`docs/plan/接口审计报告.md`），包含：
- 路由拓扑图
- 问题清单（按严重程度排序）
- 修复建议
- 附录：各批次原始审计记录

**预估工时**：小（汇总 + 交叉验证，不涉及新审计）

## 3. 批次依赖关系

```text
        批次1 (聚合边界)
              │
    ┌─────────┼─────────┐
    ▼         ▼         │
  批次2    批次3        │
 (Schema)  (结构)       │
    │         │         │
    └─────────┼─────────┘
              ▼
        批次4 (汇总)
```

- 批次 1 必须优先执行：聚合层是路径冗余和职责混合最集中的区域，批次 2 和 3 的审计范围依赖批次 1 的结论
- 批次 2 和批次 3 审计不同的反模式维度，无相互依赖，可在批次 1 完成后并行执行
- 批次 4 是前三批次的结果汇总，无可并行性

## 4. 执行规则

### 4.1 代理策略

- 每批次由独立子代理（`agent_open`，不 fork context）执行
- 子代理的审计范围限定在本批次内
- 审计代理报告问题和证据，**不做修改**
- 主代理负责整合各批次结果、交叉验证、输出最终报告

### 4.2 审计输出规范

每批次输出存入 `docs/plan/`：

```text
docs/plan/
├── 接口审计计划.md          ← 本文件
├── 接口审计-批次1-聚合边界.md
├── 接口审计-批次2-Schema统一.md
├── 接口审计-批次3-结构归属.md
└── 接口审计报告.md           ← 批次 4 输出
```

### 4.3 证据要求

每个发现需附带：
- **文件路径 + 行号**：问题所在位置
- **Schema 引用**：涉及的具体类型名
- **对比数据**：如「表达分裂」需列出两个 Schema 的字段差异
- **交叉引用**：如「路径冗余」需同时引用聚合端点和独立端点的路径

### 4.4 不做修改

审计阶段只发现问题，不修改代码。修复建议在批次 4 汇总报告中提出，不在审计过程中直接实施。

## 5. 时间估算

| 批次 | 审计对象数 | 预估子代理数 | 瓶颈 |
|------|-----------|-------------|------|
| 1 | 2 聚合 + ~10 独立端点 | 2 | Zone schema 链读取 |
| 2 | 9 实体 × ~4 接口 | 3（3 实体并行 × 3 轮） | Schema 逐字段对比 |
| 3 | ~15 嵌套结构 | 2 | 完整 Schema 定义抽取 |
| 4 | 全量汇总 | 无子代理 | 汇总质量取决于前三批 |

---

## 6. 后续行动

审计报告产出后，按问题严重程度排定修复批次：

1. **严重 + 高优先级**问题先修
2. 每个修复以独立 PR 提交
3. 修复后重跑受影响批次的审计，验证反模式已消除
