## A1：`GET /api/zones` 首页聚合

**文件**：`app/api/zone.py:15`，`app/schemas/zone.py`

**端点**：`GET /api/zones`（前缀 `/zones` 下唯一端点）

**返回结构**：

```
HomeAggregationResponse
├── banners: list[BannerBrief]           ← 来源于 Zone 表 is_banner=True 的记录
└── zones: dict[str, ZoneSectionData]    ← 按 zone_type 分组
    └── ZoneSectionData
        ├── items: list[ZoneBrief]       ← Zone 入口卡片（本域数据）
        ├── courses: list[CourseBrief]   ← 跨域：课程域数据
        └── activities: list[ActivityBrief]  ← 跨域：活动域数据
```

### 子实体对比

#### 对比 1：CourseBrief vs 独立端点 CourseListResponse

| 字段 | CourseBrief (`schemas/zone.py`) | CourseListResponse (`schemas/course.py`) | 结论 |
|------|-------------------------------|------------------------------------------|------|
| id | int | int | ✅ 一致 |
| title | str | str | ✅ 一致 |
| category | str | str | ✅ 一致 |
| description | str \| None | str \| None | ✅ 一致 |
| cover_url | str \| None | str \| None | ✅ 一致 |
| price | int | int | ✅ 一致 |
| teacher_name | str \| None | str \| None | ✅ 一致 |

**结论**：字段完全一致，但是**两个不同的 Pydantic 类型**，不是继承/复用关系。非「表达分裂」（字段一致），但属**重复定义**。

#### 对比 2：ActivityBrief vs 独立端点 ActivityResponse

| 字段 | ActivityBrief (`schemas/zone.py`) | ActivityResponse (`schemas/activity.py`) | 结论 |
|------|----------------------------------|------------------------------------------|------|
| id | int | int | ✅ 一致 |
| title | str | str | ✅ 一致 |
| description | str \| None = None | str \| None = None | ✅ 一致 |
| cover_url | str \| None = None | str \| None = None | ✅ 一致 |
| location | str \| None = None | str \| None = None | ✅ 一致 |
| start_time | datetime \| None = None | datetime \| None = None | ✅ 一致 |
| end_time | datetime \| None = None | datetime \| None = None | ✅ 一致 |
| max_participants | int | int = 0 | ✅ 一致 |
| is_active | — | bool = True | ❌ **聚合丢失** |
| created_at | — | datetime | ❌ **聚合丢失** |

**结论**：`ActivityBrief` 比 `ActivityResponse` 少 2 个字段。**反模式 #3（表达分裂）**：同一逻辑实体（Activity）在不同接口中用不同 Schema 表达。聚合接口用了缩减版。

#### 对比 3：BannerBrief vs 管理端 BannerListItem

| 字段 | BannerBrief (`schemas/zone.py`) | BannerListItem (`schemas/admin_banner.py`) | 结论 |
|------|-------------------------------|--------------------------------------------|------|
| id | int | int | ✅ |
| image_url | str | str | ✅ |
| jump_link | str \| None = None | str \| None = None | ✅ |
| sort | int | int | ✅ |
| start_time | — | datetime \| None | ❌ |
| end_time | — | datetime \| None | ❌ |
| is_active | — | bool | ❌ |
| created_at | — | datetime | ❌ |

**特殊发现**：两者**数据来源不同**：
- `BannerBrief` 从 **Zone 表**（`is_banner=True` 的记录）读取
- `BannerListItem` 从独立的 **Banner 表**（`app/models/banner.py`）读取

这意味着系统中存在两套 Banner 数据模型：一套通过 Zone 表的 banner 标记，一套通过独立 Banner 表。**这是架构层面数据不一致的潜在风险，但超出接口审计标准的四个反模式范围**。

**结论**：用户端不暴露管理字段，属于常规差异。**不触发反模式**。

### 路径冗余判定

| 接口 A（聚合路径） | 接口 B（独立路径） | 重叠数据 | 判定 |
|-------------------|-------------------|----------|------|
| `/api/zones` → `zones["study"].courses` | `/api/courses` → 课程列表 | 课程列表数据（前 10 条） | **#4 路径冗余** |
| `/api/zones` → `zones["activity"].activities` | `/api/activities` → 活动列表 | 活动列表数据（前 10 条） | **#4 路径冗余** |
| `/api/zones` → `zones[*].items` | 无用户端独立 Zone 端点 | 无冗余 | ✅ 无问题 |
| `/api/zones` → `banners` | `/admin/banners`（管理端） | 不同数据源（Zone vs Banner 表） | ⚠️ 架构差异 |

**路径冗余证据**：

- `app/services/zone.py:82-89` — 聚合接口从 Course 表取前 10 条活跃课程
- `app/api/courses.py:23-46` — 独立课程列表接口分页返回全部课程
- `app/services/zone.py:91-97` — 聚合接口从 Activity 表取前 10 条活跃活动
- `app/api/activity.py:21-36` — 独立活动列表接口分页返回全部活动

### 职责混合判定

`/api/zones` 前缀下只有一个端点 `GET ""`，该端点在一次请求中执行了：

| 操作 | 数据域 | 性质 |
|------|--------|------|
| 取 Banner（Zone 表 is_banner=True） | Zone 域 | Zone 本域数据 |
| 按 zone_type 分组取 Zone 列表 | Zone 域 | Zone 本域数据 |
| 取活跃课程 Top 10 | Course 域 | **跨域数据** |
| 取活跃活动 Top 10 | Activity 域 | **跨域数据** |

**判定**：该端点本质是首页聚合端点，zone_type 下的 courses/activities 作为专区关联数据，在 `ZoneSectionData` 内就近归属（`zones["study"].courses`），结构设计是合理的聚合模式。

但由于该端点同时返回本域 Zone 数据和跨域 Course/Activity 数据，且 URL 前缀 `/zones` 暗示「专区」，如果出现独立的用户端 Zone 列表端点，将触发「职责混合」。**当前不触发，但属于边界模糊**。

## A2：`GET /admin/statistics/dashboard` 看板聚合

**文件**：`app/api/admin/statistics.py`，`app/services/admin_statistics.py`

**端点**：`GET /admin/statistics/dashboard`

**返回结构**（`response_model=APIResponse`，无泛型）：

```python
{
    "total_users": int,           # SELECT COUNT(*) FROM User
    "total_orders": int,          # SELECT COUNT(*) FROM Order
    "recent_orders_30d": int,     # COUNT(*) WHERE created_at >= 30d
    "paid_orders": int,           # COUNT(*) WHERE status IN ('paid','completed')
    "revenue_fen": int,           # SUM(price) WHERE status IN ('paid','completed')
    "recent_revenue_30d_fen": int,# SUM(price) 30d 窗口
    "conversion_rate": float,     # paid_orders / total_orders * 100
}
```

### 与独立端点交叉对比

| 看板指标 | 独立端点 | 是否可等价获取 | 判定 |
|----------|----------|--------------|------|
| total_users | `/admin/users` PaginatedData.total | 无筛选时等价（但用户列表的 total 是分页 total，受筛选影响） | ✅ 无冗余（两者设计意图不同：一个是统计，一个是列表分页计数） |
| total_orders | `/admin/orders` PaginatedData.total | 无筛选时等价 | ✅ 无冗余 |
| paid_orders | 无独立端点 | 不可从其他端点获取 | ✅ 无冗余 |
| revenue_fen | `/admin/orders/reconciliation` 按日期对账 | 对账接口是按日统计，看板是全量 | ✅ 无冗余 |
| recent_* | 无独立端点 | 不可从其他端点获取 | ✅ 无冗余 |

**结论**：Dashboard 全部是数据库聚合函数（COUNT/SUM），不是从已有独立接口复制数据。**不触发反模式 #4**。

### 类型安全问题

`app/api/admin/statistics.py:17`：
```python
@router.get("/dashboard",
    response_model=APIResponse,   # ← 无泛型，返回裸 dict
```

`AdminStatisticsService.dashboard()` 返回 `dict`，不是 Pydantic 模型。这不属于接口审计标准的四个反模式，但违反开发规范中 `response_model` 应显式声明的约定。
