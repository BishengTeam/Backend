# 接口审计 — 批次1：二审经验

> 日期：2026-06-08
> 关联：[一审报告](./接口审计-批次1-聚合边界.md)
> 定位：一审修复后的二次审查中发现的问题 + 可复用于后续批次的审查经验

---

## 背景

一审报告识别了 6 个问题（2 个路径冗余、1 个表达分裂、1 个重复定义、1 个架构差异、1 个类型安全）。一审修复了后四个问题，但修复过程引入了新的结构性问题。二审在检查 `/api/zones` 实际响应时发现这些遗留问题。

---

## 二审发现

### 发现 1：「万能容器」Schema — 修复连锁反应的典型案例

**一审修复了什么**：`ActivityBrief` / `CourseBrief` 替换为共享的 `ActivityResponse` / `CourseListResponse`，消除了表达分裂和重复定义。

**修复引发的连锁反应**：共享 Schema 到手后，`ZoneSectionData` 被扩展为：
```python
class ZoneSectionData(BaseModel):
    items: list[ZoneBrief]
    courses: list[CourseListResponse] | None = None          # study 用
    activities: list[ActivityResponse] | None = None          # activity 用
    certifications: list[CertificationResponse] | None = None # cert 用
    trainings: list[AdminTrainingListItem] | None = None      # training 用
    competitions: list[CompetitionRegResponse] | None = None  # competition 用
    jobs: list[JobResponse] | None = None                     # employment 用
```

6 个实体字段，每个 zone section 只用 1-2 个，其余全是 `null`。实际响应中 4 个 section 累计约 40 个 `null` 字段。

**根因**：修复表达分裂时，只关注了「类型是否一致」，没关注「字段是否应该共存于同一个容器」。把「可用的共享类型」等同于「应该放在一起的字段」。

> **经验 E1**：修复一个问题后，必须检查修复引入的新结构是否产生了新的反模式。特别是：被修复的类型被复用到更多地方时，检查那些地方是否合理承载了这些类型。

### 发现 2：null 字段泛滥是 Schema 设计不当的信号

当响应中某字段对某些实例「永远为 null」，说明 Schema 类型太宽——它试图用一个类型表达多种不同的结构。

| 信号 | 含义 |
|------|------|
| 同一类型的实例，字段为 null 的比例 > 50% | 该类型是「万能容器」，应该拆分或用联合类型 |
| null 字段集中在某几个「类型标签」下 | 应该用 discriminated union 或按标签分类型 |
| 新增实体类型时，直接在容器上加 `\| None = None` | 缺少结构设计审查 |

本项目中的修复方案是在 `ZoneSectionData` 上加 `@model_serializer` 剔除 None——这是**序列化层的补救**，真正的结构问题（按 zone_type 区分实体类型）需要数据模型层解决（如 Zone 表与实体表建立外键关联）。

> **经验 E2**：审计响应 JSON 时，统计每个字段的 null 比例。null 比例超过 50% 的字段，标记为「Schema 过宽」信号。后续批次应该把「null 字段比例」加入审计检查项。

### 发现 3：硬编码的类型映射应替换为数据驱动配置

一审后 Service 中的实体分配逻辑：
```python
if ztype == "cert":
    section.certifications = certifications
elif ztype == "study":
    section.courses = courses
elif ztype == "competition":
    section.competitions = competitions
elif ztype == "activity":
    section.activities = activities
elif ztype == "employment":
    section.jobs = jobs
elif ztype == "training":
    section.trainings = trainings
```

这段代码的本质是一个 **lookup table**——用代码的分支结构伪装成的映射表。后果：
- 新增 zone_type 要改 3 处：`ALL_ZONE_TYPES`、`ZoneSectionData` 字段、if/elif 分支
- 容易漏改其中一处
- 映射关系散落在代码中，不易审计

**修复**：提取为 `ZONE_ENTITY_MAP` 字典（在 Schema 层）+ `_ENTITY_QUERIES` 字典（在 Service 层），一个循环替代 6 个分支。

> **经验 E3**：审计时如果发现 3 个以上的 if/elif 分支在做同构的类型→操作映射，标记为「伪装 lookup table」。要求提取为数据驱动的映射配置。后续批次把此作为固定审计检查项。

### 发现 4：Schema 与 Service 的实体配置必须可交叉验证

`ZONE_ENTITY_MAP`（zone_type → 字段名）在 `schemas/zone.py`，`_ENTITY_QUERIES`（字段名 → 查询配置）在 `services/zone.py`。两者的键集必须一致。

**实际验证**：
```python
assert set(_ENTITY_QUERIES.keys()) == set(ZONE_ENTITY_MAP.values())
assert set(ALL_ZONE_TYPES) == set(ZONE_ENTITY_MAP.keys())
```

> **经验 E4**：跨模块的配置映射对（Schema 的字段定义 ↔ Service 的查询配置）需要可机械验证。理想情况下通过类型系统约束（如 TypedDict + Literal），最差情况下加 assert 检查。后续批次审计时，主动检查这类跨模块映射一致性。

### 发现 5：路径冗余需要区分「设计冗余」和「实现冗余」

一审将 `/api/zones` 中的 courses/activities 与独立 `/api/courses`、`/api/activities` 判定为路径冗余（高严重度）。二审确认此问题**仍未修复**——且新增了 certifications/jobs/trainings/competitions 四条路径冗余。

但这个问题的本质需要区分：

| 类型 | 特征 | 处理方式 |
|------|------|---------|
| **设计冗余** | 聚合端点和列表端点服务不同产品场景（首页预览 vs 分页浏览），有意为之 | 文档化差异，标注为「设计冗余」而非缺陷 |
| **实现冗余** | 两个端点返回完全相同的 Schema 和相同的业务语义，前端可以互换调用 | 应合并或废弃其中一个 |

`/api/zones` 返回「各实体 Top 10」是无分页无筛选的预览，`/api/courses` 返回分页可筛选的完整列表——属于设计冗余，不应标记为 bug。但需要在 API 文档和审计报告中明确标注，避免后续批次重复报告。

> **经验 E5**：审计路径冗余时，先判断冗余是「设计冗余」还是「实现冗余」。设计冗余（不同产品用途的相同数据视图）通过文档标注解决；实现冗余（可互换的重复端点）才需要代码修复。

### 发现 6：只看代码看不出 null 问题——必须看序列化输出

`ZoneSectionData` 的 null 字段在 Python 对象层面完全「正常」：字段有默认值 `None`，Pydantic 校验通过，类型检查通过。只有看到实际的 JSON 响应才能发现 40 个 null。

> **经验 E6**：审计接口时，必须获取实际的 HTTP 响应 JSON（不是 Python 对象的 `__repr__`，不是类型定义）。Pydantic `model_dump()` 的输出和 `response_model` 序列化结果可能不同。建议在每个批次中至少对一个端点做端到端响应抓取。

## 可复用的审查检查项（给后续批次）

以下检查项应加入后续批次的审计流程：

### 响应级检查

- [ ] **null 字段比例**：统计响应 JSON 中每个字段的 null 出现频率。null 比例 > 50% → 标记「Schema 过宽」
- [ ] **同类型实例的字段差异**：同一 Schema 类型的不同实例（如不同 zone_type 的 ZoneSectionData），字段集合是否一致？不一致 → 标记「万能容器」

### 代码级检查

- [ ] **伪装 lookup table**：同一函数内 ≥3 个 if/elif 分支做同构的类型→值映射 → 标记「硬编码映射」
- [ ] **跨模块配置一致性**：Schema 中定义的字段名集合与 Service 中使用的字段名集合是否一致？→ 要求可机械验证
- [ ] **新增字段时的容器膨胀**：当为一个已有容器类型新增 Optional 字段时，检查该字段是否对所有实例都有意义

### 修复后检查

- [ ] **连锁反应**：本次修复改动的类型被哪些地方引用？引用处是否合理承载了这些类型？
- [ ] **null 回归**：修复后重新抓取响应 JSON，确认没有引入新的 null 泛滥

## 后续批次的审计顺序建议

基于一审/二审的经验，建议后续批次按以下顺序进行（从最容易出问题的开始）：

1. **聚合端点**（如首页、Dashboard 等返回多域数据的端点）— 最容易出现 Schema 过宽、硬编码映射、null 泛滥
2. **管理端列表端点** — 容易与用户端列表端点产生表达分裂
3. **CRUD 端点** — 检查请求/响应 Schema 是否与独立列表端点一致
4. **上传/文件端点** — 检查 URL 生成逻辑是否一致
