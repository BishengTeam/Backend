# 用户信息模块 冒烟测试逻辑

> 测试服务：`127.0.0.1:8000`
> 测试用户：seed_testdata 创建的测试用户（openid: test_openid_user_001）
> 管理端 token：通过 POST /admin/auth/login 获取管理员 token

---

## 测试流程（15 步）

### 0. 准备

```
1. 获取用户 token（调用 POST /api/auth/login 或使用 seed_testdata 已有 token）
2. 获取管理员 token（POST /admin/auth/login { "username": "admin", "password": "admin123" }）
```

---

### 第一阶段：Level 1 基础资料（无需审核）

```
步骤 1: GET /api/user/profile
  → 期望 200，data 包含 id, openid, nickname=null, email=null, phone=null
  → 期望 identity_status=null（未提交实名）

步骤 2: PUT /api/user/profile { "nickname": "测试昵称", "email": "test@example.com" }
  → 期望 200

步骤 3: GET /api/user/profile
  → 期望 nickname="测试昵称", email="test@example.com"
  → 验证：修改不需要审核，直接生效
```

---

### 第二阶段：Level 2 实名认证（需审核）

```
步骤 4: POST /api/user/identity
  {
    "user_type": "student",
    "real_name": "张三",
    "id_card_number": "510106199001011237",
    "id_card_front_oss": "oss://front.jpg",
    "id_card_back_oss": "oss://back.jpg"
  }
  → 期望 200，status="pending"
  → 期望 gender="男", age=36(约), census_register="成都市-金牛区"

步骤 5: GET /api/user/identity
  → 期望 id_card_number 脱敏（5101**********1237）

步骤 6: GET /api/user/profile
  → 期望 identity_status="pending"
  → 期望 user_type="student", real_name="张三", gender="男"
  → 期望 phone=null, id_card_raw=null（审核未通过，用户端不返回明文）

步骤 7: 管理员审核通过
  PUT /admin/users/{user_id}/identity/review { "status": "verified" }
  → 期望 200

步骤 8: GET /api/user/profile（审核通过后 — 用户端）
  → 期望 identity_status="verified"
  → 期望 phone 返回脱敏值（格式: 138****1234），id_card 返回脱敏值（5101**********1237）
  → 期望 id_card_raw=null（用户端 profile 始终不返回明文身份证）

步骤 8a: 管理端查看用户 profile（审核通过后 — 明文验证）
  GET /admin/users/{user_id}/profile
  → 期望 200，identity_status="verified"
  → 期望 phone 有值（明文手机号）
  → 期望 id_card_raw 有值（明文身份证号）
```

---

### 第三阶段：学生/企业互斥

```
步骤 9: POST /api/user/enterprise { "organization": "某公司" }
  → 期望 422，提示"当前为学生用户，请先切换用户类型"

步骤 10: POST /api/user/student
  {
    "education": "本科",
    "school": "四川大学",
    "major": "计算机科学",
    "student_card_oss": "oss://student.jpg"
  }
  → 期望 200，status="pending"

步骤 11: 管理员审核学生信息
  PUT /admin/users/{user_id}/student/review { "status": "verified" }
  → 期望 200
```

---

### 第四阶段：审核驳回恢复

```
步骤 12: 重新提交实名（修改姓名）
  POST /api/user/identity
  {
    "user_type": "student",
    "real_name": "张四",
    "id_card_number": "510106199001011237",
    "id_card_front_oss": "oss://front2.jpg",
    "id_card_back_oss": "oss://back2.jpg"
  }
  → 期望 200，status="pending"，real_name="张四"

步骤 13: 管理员驳回
  PUT /admin/users/{user_id}/identity/review { "status": "rejected" }

步骤 14: GET /api/user/identity
  → 期望 status="rejected"，real_name 恢复为 "张三"（snapshot 恢复）
```

---

### 第五阶段：edit_count 限制（需单独测试，可能消耗真次数）

```
连续提交 5 次 Level-2 修改 → 第 6 次应返回 422
  "实名/学生/企业信息最多修改 5 次，30 天后重置"
```

---

## 测试要点总结

| # | 测试点 | 预期 |
|---|--------|------|
| L1-编辑 | 修改昵称/邮箱 | 直接生效，无审核 |
| L2-提交 | 提交实名 | status=pending，身份证衍生字段自动计算 |
| L2-脱敏 | 用户端查身份证 | 脱敏 5101**********1237 |
| L2-审核 | 管理员审核通过 | status=verified；用户端 phone/id_card 脱敏不返回明文；管理端 GET /admin/users/{id}/profile 返回明文 phone 和 id_card_raw |
| 互斥 | 学生用户提交企业信息 | 拒绝，返回 422 |
| 驳回 | 管理员驳回 | snapshot 恢复旧值 |
| 次数 | 修改 6 次 Level-2 | 5 次成功，第 6 次返回 422 |
