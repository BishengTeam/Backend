# 多报考项目与批次配置版本

人社项目沿用 `cert_product` 的稳定身份，编码由服务端生成。业务识别依据 `type=renshe`，`RS-ZY` 仅用于经核实的旧数据兼容。每次规则变化新增 `renshe_project_config` 版本；批次保存版本外键、配置快照和当时项目名称，报名材料版本记录对应配置外键。

后台入口为“报考项目”，采用与 H3C/NISP 一致的表格、工具栏和编辑弹窗。新增项目不要求产品编码、英文名或产品价格；费用由批次管理。项目更新不自动升级草稿，草稿页提示并提供明确更新操作；发布后不能更换项目或核心报考属性。

## 本次已适配能力

- 职业、外部申报职业代码、技能等级及等级导出值可配置，一个项目固定一个职业与等级。已有批次后更换组合须新建项目。
- 新考、补考；学历型申报。
- 相关专业在读应届学生：系统校验已审核实名、学生资料及可配置学历范围，专业相关性与应届资格由审核人员核实，不声称系统已自动判定。
- 联系电话、通讯地址、邮箱三个必填报名字段。
- 六种已有私有材料槽位；身份证正反面及照片必填，其余可以设为选填；每种一份，JPG/JPEG 或学信网 PDF，保留原有大小、MIME、文件头和归属校验。
- `renshe_registration_v1` 使用已提供的真实 25 列报名信息模板；`renshe_roster_v1` 为系统生成的 11 列内部汇总表，不能将其当作外部主管部门已经认可的新申报模板。两者都附现有工作经历模板，支持受控字段映射和按考生／材料类型两种附件目录。
- 不支持的规则、字段、材料数量或模板只允许保存草稿，禁止创建／发布批次。没有实现脚本执行或上传任意 Excel 即成为可用模板。

项目状态与批次状态独立。停用或改回草稿只阻止创建、发布批次；已有已发布批次继续按固定配置接受报名、补正、审核、导出与退款。停止招生须关闭具体批次。

权限沿用项目配置 `content:write`、批次 `user:write`；新增独立的 `renshe:review` 和 `renshe:export`，赋予现有认证管理员角色。退款处理仍只允许超级管理员，退款查看沿用 `order:list`。

导出创建前检查模板、固定配置、报名版本、必填材料、字段完整性和人员范围。任务重试保留创建时选定的报名及材料版本，不再重新选择当前版本。

## 部署与迁移

1. 在目标环境先运行 `python -m scripts.audit_renshe_projects`，保存只读核查报告。核实其中异常订单、退款、导出和待确认批次。
2. 备份数据库后运行 `alembic upgrade head`，新增迁移 `rsh003_project_versions`。迁移仅把职业、职业代码、等级、考试与申报类型完全匹配的旧 `RS-ZY` 批次关联到旧项目 V1。不改变订单金额、退款金额或既有导出文件，不创建虚假业务审计。
3. 其他已有项目保留为待配置草稿；无法确认的批次保留原状，迁移日志列出其 ID。核实后单独处理，不自动把全部数据归入默认项目。
4. 配置 `RENSHE_TEMPLATE_DIR` 指向包含本目录 `报名信息.xlsx`、`工作经历.xlsx` 的实际绝对目录。发布与导出均检查模板文件及结构。沿用原有私有存储、下载有效期和退款配置。
5. 同步发布 Backend、Admin、Platform。新版本小程序使用 `/api/renshe/projects` 与 `/api/renshe/batches`，直接批次链接保持可用。
6. 在 PostgreSQL 测试环境运行迁移和现有 `integration_db` 套件，并接通测试微信支付／退款通知完成部署验收。本地 SQLite 隔离回归验证业务和文件内容，不证明 PostgreSQL 行锁或真实支付网关可用。

新增项目已经关联批次后，迁移禁止直接降级到单项目模型；应采用单独审核的数据回滚计划。该代码改动未执行任何业务数据库迁移。

## 回归证据

`tests/unit/test_renshe_projects.py` 使用临时数据库和实际私有文件存储，覆盖两个项目各多个批次、报名与支付履约、初审、两种真实生成的 Excel/ZIP 文件内容、外审和专用退款；同时覆盖版本冻结、草稿主动升级、停用继续办理、不可变配置、未知能力发布阻断及跨项目 ID 伪造。
