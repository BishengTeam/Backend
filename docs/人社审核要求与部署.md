# 人社审核要求与部署

报名详情按每个版本绑定的 `project_config_id` 解析实际申报路径，返回资料分组、材料要求、核验清单和依据文件。审核提交在原事务和付款锁内重新解析同一份要求，必须带当前版本 ID、完整且准确的核验 key，以及有效的必填材料记录。无法确认历史配置时明确阻断，不使用当前产品默认配置代替。

初审通过时，服务端保存 `checklist_snapshot`，记录当次路径、核验定义和版本关联；历史记录不回填或改写。旧客户端缺少新路径核验项时必须刷新后台后再审核。补正生成新版本后，旧版本审核请求会失败。

## 发布顺序

1. 先执行数据库迁移到 `rsh008_review_requirements`（新增可空 JSON 字段）。
2. 发布包含动态审核要求和资料文件接口的 Backend。
3. 发布对应 Admin；清理旧静态页面缓存。PDF 依据采用鉴权 Blob 预览，Admin CSP 的 `frame-src` 需保留 `blob:`。

五份依据文件随 Backend `docs/renshe/references/` 打包，Dockerfile 将目录设为只读。也可设置 `RENSHE_REFERENCE_DIR` 指向只读挂载目录，文件名称须保持原名。接口只接受固定资料 ID，继承报名详情的 `user:list` 权限，返回私有、禁止缓存的响应。

回滚应用时保留新增字段、核验快照和已提交版本；迁移禁止破坏性降级。上线环境还需验证实际管理员权限、签名材料地址与 PDF 预览。

## 验证入口

- `tests/unit/test_renshe_review_requirements.py`：每个已开放职业组合及具体三级路径的材料矩阵、核验 key、补正字段和未适配阻断。
- `tests/unit/test_renshe_references.py`：权限、白名单、文件部署及原始文件响应。
- `tests/integration/db/test_renshe_review_revision.py`：使用独立 PostgreSQL schema，真实补正提交与初审并发，旧版本拒绝、订单复用和核验快照持久化。
- Admin `tests/pages/renshe-review.test.tsx`、`material-preview.test.tsx`：核验隔离、历史只读、中文字段、可见区域加载、预览重试及过期请求隔离。

PostgreSQL 测试必须同时设置独立测试库的 `TEST_DATABASE_URL` 与 `TEST_DATABASE_URL_SYNC`，且先完成迁移；不得指向生产库。Linux 部署脚本及真实部署环境预览需在对应环境验收。
