# 接口审计标准

## 坏接口 — 四个反模式

| # | 反模式 | 判定 |
|---|--------|------|
| 1 | **职责混合** | 一个 URL 前缀下同时承载聚合和单域透传两种语义 —— 两种职责，两种处理逻辑 |
| 2 | **结构散落** | 同一概念的数据拆在两个层级：元数据在一层，实际内容在另一平级层 —— 前端跨层组装 |
| 3 | **表达分裂** | 同一实体在不同接口中字段数不同 —— 有的少字段，有的多字段 —— 没有单一信息源 |
| 4 | **路径冗余** | 聚合层返回的数据与业务域独立端点返回的数据存在交集 —— 同一数据有多条获取路径 |

## 好接口 — 四条基准

| # | 基准 | 判定 |
|---|------|------|
| 1 | **单一职责** | 一个接口或一个 URL 前缀只做一件事：聚合就是聚合，列表就是列表 |
| 2 | **就近归属** | 专区数据放在专区 key 下，不散落在平级字段 —— 拿到 key 就拿到完整内容 |
| 3 | **统一表达** | 同一实体在所有接口中使用同一个 Schema —— 不因调用路径不同而字段增减 |
| 4 | **无重叠** | 聚合层只做编排，不重新承载业务域已有独立端点的数据 |

## 审计步骤

1. 看 URL 前缀 —— 有没有混入不同职责的子路径
2. 看返回结构 —— 同一概念的数据是否被拆到多个层级
3. 看 Schema 引用 —— 同一实体是否用了多个不同的 DTO
4. 看数据来源 —— 聚合接口是否返回了已有独立端点的数据
